### Claim-by-claim verification

1. **"Spawned subagents now lease, including model-dispatched one-shot spawns, not just actors."**
   Read `lib/lain/tools/subagent.rb`. `#perform` (the model-dispatch entry point) calls
   `spawn_one_shot` for `@mode != :actor`, which calls `#run_child`, which does
   `isolation.hold(@name, journal:) { |worker_env| ... }` **unconditionally** — the method's own
   comment says "the lease is taken UNCONDITIONALLY... there is no `if isolation` here." The
   `isolation` object is `Tools::Subagent::Leases`, constructed in
   `lib/lain/cli/wiring/toolset_build.rb#spawn_seam` as
   `Lain::Tools::Subagent::Leases.new(backend: isolation)` where `isolation:` is the injected
   `fleet_isolation`. So a plain, model-dispatched `subagent` tool call now leases from the real
   backend when `--isolation worktree` is passed — previously (per the card's framing, which I did
   not need to independently verify via git history since the card states it directly) this path
   did not.

2. **"Every model-dispatched spawn acquires a lease for the dispatch and releases it after,
   including a nested spawn, so a grandchild does not escape into the host."** Verified in
   `Tools::Subagent::Leases#hold` (same file): `lease = @backend.acquire(...)`, `yield(...)`,
   `ensure reclaim(lease, worker, journal)` — acquire/release bracket one dispatch. `#descend`
   builds a nested copy via `@builder.config(parent:)`, which passes `seam: @seam.with(parent:)` —
   the **same** `isolation:` (the same `Leases` instance, same backend, same worker-id counter)
   travels to the nested `Subagent`, so a grandchild's dispatch leases and releases through the
   identical mechanism, at its own worker id (`Isolation::WorkerId.spawned(role:, ordinal:
   next_ordinal)`), never the host's or the parent's checkout.

3. **"The main chat's own session is still never isolated."** Verified in
   `lib/lain/cli/wiring.rb#chat_env`: `Lain::WorkerEnv.default.with(cwd: project.cwd)`, with the
   comment "Deliberately not a leased environment... the user's own edits belong in the user's own
   tree." Unchanged; kept in both descriptions.

4. **"A run resolves exactly ONE isolation backend and shares it between the fleet path and the
   spawn path."** Verified in `lib/lain/cli/wiring.rb`: `fleet_isolation` is memoized
   (`@fleet_isolation ||= IsolationBackend.resolve(...)`) and handed to both `Supervisor.new(...,
   isolation: fleet_isolation)` (line ~188) and `build_toolset` → `ToolsetBuild.new(...,
   isolation: fleet_isolation, ...)` (line ~336), which wraps it into the `Subagent::Seam` at
   `toolset_build.rb#spawn_seam`. One resolution, two consumers.

5. **"`redis` is no longer a declarable service."** Verified in
   `lib/lain/isolation/services/builder.rb`: `VERBS = %i[postgres compose].freeze`, and `#redis` is
   a defined method that only raises `Retired`, pointing the operator at a `compose` declaration
   instead. Grepped the touched planning docs and `exe/lain` for "redis" — no mentions existed
   there to begin with, so nothing needed changing on that front.

6. **"The backends `--isolation` accepts are unchanged."** `Lain::CLI::IsolationBackend::BACKENDS
   = %w[none worktree].freeze` — confirmed unchanged, and both descriptions interpolate this
   constant rather than restating it, so they cannot drift from the resolver.
