## A note for the reviewer: why two doubles broke, and why widening was still right

`Command.new(args: [...], lua: ...)` in `rpc_thread.rb` documents the reason on its own
line: holding the argument LIST rather than named fields is what lets one queue and one
`#send_command` serve every entry point of different arity, from `post_render`'s one
argument to `set_review`'s three. That is a deliberately positional wire, and
`ApprovalView#posted` calling `@rpc.set_approval(lines, generation, rows, calls)` is the
same idiom on the Ruby side of it — widening a fixed ordinal list from 3 to 4 was the
natural extension, not a design smell.

The cost of a positional idiom is that anything standing in for the far end has to match
its arity exactly, and a hand-rolled test double is exactly that: two of them
(`approval_view_spec.rb`'s `SpyRpc`, `surfaces_spec.rb`'s anonymous `rpc` double) spelled
out `set_approval(lines, generation, rows)` literally, so the fourth argument was a hard
`ArgumentError`, not a silent no-op. The one double in the tree that DIDN'T break
(`surfaces_spec.rb:262`, `def set_approval(*) = raise(ClosedQueueError)`) is arity-
agnostic by construction — `(*)` is the shape a positional wire's double should be
written in if it is ever going to grow a parameter again, and the two that broke are the
shape that can't. Worth a line in review, not a change now: neither double asserts
anything about `calls` (nothing in either file references it), so there was nothing to
retrofit beyond the arity itself.

### 2 and 3, together: `call_of` per-line, and the quadratic wire payload

These turned out to be one design defect with two measured costs, and fixing the shape
that caused the first fixes the second for free. `rendering_of` used to build `owners`
(one pending per LINE, by design -- multi-line items need every line to answer the same
call) and then map `call_of` over `owners` to build `calls` -- so a wrapped item's
`.inspect` ran once per line it wraps into, and the array that RESULT built duplicated
the same string once per line before it ever reached msgpack.

Redesigned `Rendering` to carry `calls` as ONE ENTRY PER PARKED CALL (computed once,
in `rendering_of`'s own `parked.map { |pending| call_of(pending) }`, then threaded into
`lines_for`/`summary_for` so the SAME string is reused rather than recomputed for the
row-text too) and added `call_index`, `owners`'-shaped (one entry per row, 1-based),
naming which member of `calls` a row resolves to. A lua reader does
`calls[call_index[N]]` for row N's command in full -- `Rendering`'s own comment is now
the ONE place that reasoning lives (see the NIT below). `owners` itself is unchanged
and still Ruby-only, never crossing the wire -- `#at`/`#decide` never needed `calls` at
all, only `Rendering#calls`/`#call_index` are new members threaded through
`posted -> @rpc.set_approval` (now 5 args) -> `RenderInlet`/`RenderQueue` ->
`SET_APPROVAL`'s lua string -> `62_approval.lua`'s `set_approval`, which now stamps a
SECOND new buffer variable, `b:lain_approval_call_index`, beside `b:lain_approval_calls`
(now itself linear-sized).

`rendering_of`'s ABC size tripped `Metrics/AbcSize` at this shape; extracted two
one-line collaborators, `owners_for(items, parked)` and `call_index_for(items)`, per
CLAUDE.md's rule against loosening the limit -- `rubocop lib spec bin` is clean.

**Measured** (own reproduction, methodology differs slightly from the panel's so the
absolute numbers are not identical, but the shape and order of magnitude match):
- Time, one 64KB-command pending, `rendering_of` alone: naive per-line design
  **475.99ms**; this design **1.63ms** (both measured `rows: 699`, matching the panel's
  row count exactly). The panel's own numbers were 586ms -> 0.8ms.
- Wire payload (`msgpack` gem, `to_msgpack.bytesize`), the `calls` argument alone:
  4KB input **0.18MB** (per-row) -> **4.1KB** (linear) + 48B `call_index`; 32KB input
  **10.95MB** -> **32.8KB** + 671B; 64KB input **43.71MB** -> **65.6KB** + 1.7KB. The
  panel's own numbers: 191KB/11.5MB/45.8MB for the per-row shape -- close enough
  (differences are wrap-column-estimate noise in my synthetic script, not a different
  claim) to confirm the SAME defect and the SAME fix.

**Red, before the fix** (temporarily reverted `rendering_of` to the naive per-line
