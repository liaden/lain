# T5 hand-back — say whether the stream ever terminated

## Files changed

### `lib/lain/telemetry/truncated_stream.rb` — NEW
`Telemetry::TruncatedStream`, a `Data.define(:kind, :model, :frames, :accumulated_bytes)` that
`include Journalable`, with a named `Carriers::TruncatedStream` guard — the
`Telemetry::MalformedResponse` shape, field for field (`kind&.to_sym` before the guard so a
String `kind` is not refused with a message naming the rejected value as the wanted one;
`model&.dup&.freeze` and nil-tolerant, because a stream that died before its first line never
named a model).

- `kind` is a closed enum of two readings a human acts on differently:
  - `:unterminated` — no terminal frame ever arrived; the prose is a fragment and the stop
    reason is fiction.
  - `:counts_absent` — a terminal frame *did* arrive, so the prose is whole, but it carried no
    `prompt_eval_count`/`eval_count` and the turn will report as free.
- `frames` and `accumulated_bytes` are guarded by `numericality` (`only_integer`, `>= 0`) and
  **not** `presence:` — a stream severed before its first line legitimately reports zero on
  both, and that is the shape most worth recording. A nil still fails.
- Journals as `truncated_stream` (`String#underscore` of the class basename, no override).

## Scoping the record to the returned attempt

Two examples, and the second is the one that makes it a scoping claim rather than a coincidence:

- *"says nothing about a severed attempt that a clean retry replaced"* — chunk 0 is a
  content-only (severed) stream, `abandon_after: 0` fires the real `RetryTap::Attempt#abandon`
  that `@retries.open_attempt { assembler.reset }` registered, chunk 1 is a terminated stream.
  The journal is empty.
- *"records the attempt actually returned, even when a discarded one had terminated"* — the
  mirror image: chunk 0 is a **complete** stream (done line, counts), abandoned; chunk 1 is
  truncated. One `truncated_stream` record, `frames: 2` — the survivor's count, not 5.

The mechanism is that the counters live in `#reset`'s one list, so the discard that already
throws away an abandoned attempt's prose throws away its frames and its terminal flag with it.
The assembler holding the bytes that reached the caller is the only one that can speak, and it
is the one `#stream_body` asks.

## Decisions worth a reviewer's eye

- **`#build_body` still writes `"done" => true`.** The card frames this as "the producer says
  what happened" with sibling cards hardening the readers, and the third escalation trigger says
  a truncated stream must not stop returning its content. Flipping `done` to `@terminated` would
  change what `#decode_stop_reason` and `#build_usage` see on the streaming path only, breaking
  path parity. The record is the whole change; the body is handed on untouched.
- **`accumulated_bytes` is message text (content + thinking), not wire bytes.** "The bytes
  accumulated" reads as the class's own accumulators, and content-plus-thinking is the figure
  that says how much of an answer the truncation left behind. Bytes rather than characters
  because the figure is about how far the stream got.

## Fix 1 — `#truncation` no longer has an ordering constraint to get wrong

Taken as you proposed: **`#truncation` idempotently drives the same flush `#result` does.** The
flush was extracted from `#result` into a private `#flush_trailing_line` that both call; after
the first one the buffer is empty and it is a no-op, so the two may be asked in either order and
the contradictory-answer window closes. `@scanned` goes back to 0 with the bytes it indexed —
it is an offset *into* the buffer, and leaving it past the end of an emptied one would make a
later `#feed` skip the newline it points beyond. That was latent in the old `#result` too and is
now fixed as a side effect rather than left for the same second caller.

The docstring no longer says "MUST BE READ AFTER `#result`", because nothing has to.

**Feature envy, tidied in the same change.** `#truncation` now returns **nil or one frozen Hash**
keyed exactly as the record's own fields — `{kind:, model:, frames:, accumulated_bytes:,
tool_calls:}` — and the public `#frames` / `#accumulated_bytes` readers are gone (they are
private detail now). The emitter is one read against one object:

```ruby
def note_truncated_stream(assembler, request)
  reading = assembler.truncation
  return if reading.nil?

  @journal << Telemetry::TruncatedStream.new(**reading, request_digest: request.digest)
end
```

`model` travels with the counts instead of being re-derived off the body, so `#stream_body` no
longer passes `body` at all. The `#result`-first comment is deleted with the constraint it
described. The kind logic moved to a private `#unreported`, named for what is missing so the nil
arm reads as "nothing went unreported".

Red for this one — the hazard reproduced exactly as the probe described it:

## Fix 3 — a severed tool call is no longer "delivered nothing"

**I took the separate `tool_calls:` count, not folding the bytes in.** Reasons, in the record's
docstring:

- The actionable fact is **how many calls were in flight**, not how much serialized JSON they
  came to. "Three tool calls arrived and then it died" is a sentence an operator acts on; "412
  bytes" is not.
- Folding them in would make `accumulated_bytes` mean two things at once — prose a user sees plus
  wire JSON they never do — and the field's whole job is to be one honest number. A reader
  comparing it against the turn's text would then find it inflated with bytes that are not in the
  turn.
- The count is free and exact: `@tool_calls` is already the parsed array.

A stream severed after three tool-call frames now journals `frames: 3, accumulated_bytes: 0,
tool_calls: 3` — distinguishable from three empty keepalives, which journal `tool_calls: 0`.

# Landing fix — the torn-line cursor, both twins

Mechanical, as directed. No git commands run.

## What changed

`ingest` raises on a torn line, so `ingest(@buffer.slice!(…))` empties the buffer while `@scanned`
still indexes what used to be in it. Both sites now **slice into a local, zero the cursor, then
parse**:

```ruby
def drain_complete_lines
  while (index = @buffer.index(NEWLINE, @scanned))
    line = @buffer.slice!(0, index + 1)
    @scanned = 0
    ingest(line)
  end
  @scanned = @buffer.bytesize
end

def flush_trailing_line
  return if @buffer.empty?

  line = @buffer.slice!(0, @buffer.bytesize)
  @scanned = 0
  ingest(line)
end
```

`drain_complete_lines` got the same treatment even though it predates the card — it is the
identical shape in the same file, and fixing one twin reads as an oversight rather than a
decision. Its comment points at `#flush_trailing_line`, which carries the reasoning once so the
two cannot rot apart. Both note that the path is unreachable through the provider today (a parse
error becomes `APIError` and the assembler is dropped), so this is hardening, not a defect.

Note the `while` exits via the exception, so the trailing `@scanned = @buffer.bytesize` is skipped
— but the cursor is 0 by then, which is the conservative offset into a buffer that still holds
every undrained line. That is the property the examples below pin.

## Panel notes carried into the record

- **The `tool_calls` NIT was withdrawn**, the panel preferring the counter-argument: folding
  tool-call payload into `accumulated_bytes` would make that field mean prose-the-user-sees and
  wire JSON at once, so a reader checking it against the turn's text would find it inflated. The
  separate count stands.
- **The `@scanned` reset in `#flush_trailing_line` was upgraded from incidental to required.**
  Removing the ordering constraint is what makes a mid-stream `#truncation` legal at all, so the
  stale offset had to go with it. Verified across ~250 byte-steps of a partial multibyte feed,
  after a flush, after flush-then-more-bytes, and after `#reset` from a half-line state. It closes
  a real regression: flush-then-feed now drains newlines where the stale offset previously skipped
  them.
- **Nothing was traded away by `TruncatedStream.new(**reading, …)`.** The seam examples drive a
  real `Provider::Ollama` through that path on every suite run, so key drift in either direction
  is a red suite rather than a 3am `ArgumentError` — `Data.define`'s keyword init rejects an
  unknown key exactly as the record's signature rejects a missing one. `truncation.keys ==
  TruncatedStream.members - [:request_digest]`, and the Hash is frozen. No extra pin wanted.
