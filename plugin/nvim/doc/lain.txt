1. INTRODUCTION                                            *lain-introduction*

This plugin is deliberately thin. Everything protocol-shaped -- the `lain://`
buffers, the `:LainSend`/`:LainReply`/... commands, all RPC handling -- is
injected into the editor by the lain gem's own runtime at attach time, so gem
and editor code can never drift. The plugin only owns the conventions AROUND
that contract:

  - a deterministic per-project server socket, so `lain chat --nvim` finds
    your editor with no flags (|lain-socket|)
  - `lain.socket_path()` and `lain.status()`, two read-only conveniences
  - `:LainStart`, a window layout over the injected buffers (|lain-api|)
  - this document, which describes the attach contract as a config consumer
    sees it (|lain-contract|)

The plugin defines no buffer logic and handles no RPC. Everything in section
|lain-contract| works identically with the plugin uninstalled
(|lain-zero-install|).

==============================================================================
2. SETUP                                                          *lain-setup*

The plugin directory ships inside the lain gem at `plugin/nvim`. Add it to
'runtimepath' (directly, or through your plugin manager pointing at that
directory) and call: >lua

    require("lain").setup({})
<
setup() records your options, defines |:LainStart|, starts listening for
attaches, and serves the project socket. Serving happens on |VimEnter| -- or
immediately when VimEnter has already fired, so lazy-loading plugin managers
that call setup after startup still get a socket.

==============================================================================
3. CONFIGURATION                                          *lain-configuration*

Every key can be given to setup(), or as `vim.g.lain_<key>` -- precedence is
setup opts, then `vim.g.lain_*`, then the default. `vim.g` values are read at
use time, so they work even without calling setup().

    key             default                  meaning ~
    socket          nil                      full socket path; overrides the
                                             whole computation in |lain-socket|
    socket_dir      nil                      base dir for the runtime-dir
                                             socket; nil means
                                             $XDG_RUNTIME_DIR/lain (or
                                             /tmp/lain)
    project_socket  ".lain/nvim.sock"        in-tree socket path, used when
                                             the project has a .lain/ dir
    state_path      ".lain/state.json"       where |lain.status()| reads;
                                             relative paths resolve against
                                             the editor's cwd
    serverstart     true                     serve the socket on VimEnter;
                                             set false to opt out
    layout          journal | timeline,      |:LainStart|'s window layout: a
                             inbox,          list of columns (left to right),
                             request         each a list of lain:// buffer
                                             names (top to bottom)

==============================================================================
4. THE SERVER SOCKET                                             *lain-socket*

The socket path is deterministic from the project directory, so lain (and any
other tool) can find this editor from the cwd alone:

  - if `cwd/.lain` is a directory, the socket lives in-tree at
    `cwd/.lain/nvim.sock` (the `project_socket` option) -- the same "beside
    the project, like .git/" convention as `.lain/state.json`;
  - otherwise it is `$XDG_RUNTIME_DIR/lain/nvim-<sha256(cwd)[:12]>.sock`
    (falling back to `/tmp/lain/...` without XDG_RUNTIME_DIR).

The first instance in a project wins the socket. A socket file left behind by
a crashed instance is reclaimed: a live owner answers a probe connect, a
stale file refuses and is removed before |serverstart()|. Two instances
started at the same instant can race the probe; the loser's serverstart
fails quietly and it simply serves no socket.

5. COMMANDS AND FUNCTIONS                                           *lain-api*

                                                                  *:LainStart*
:LainStart              Open a window layout (new tab) over the injected
                        lain:// buffers, per the `layout` option. Only
                        buffers the runtime has actually created are placed.
                        If lain has not attached yet, the layout opens
                        automatically the moment it does.

                                                          *lain.socket_path()*
lain.socket_path()      The deterministic socket path for the current
                        project (|lain-socket|). Pure -- computes the path,
                        creates nothing.

                                                               *lain.status()*
lain.status()           The decoded contents of `.lain/state.json` (the
                        state feed the running lain session publishes for
                        the tmux HUD), or nil when no session has published.
                        The gem writes the file atomically, so a read never
                        sees a half-written state.

                                                                *lain.setup()*
lain.setup({opts})      See |lain-setup| and |lain-configuration|.

6. THE ATTACH CONTRACT (PROTOCOL 8)                            *lain-contract*

Everything below is provided by the gem's injected runtime, not by this
plugin, and works without the plugin installed. It is documented here because
it is the surface your own config hooks.

------------------------------------------------------------------------------
6.1 USER EVENTS                                                  *lain-events*

The runtime fires |User| autocmds as its stable surface -- hook these, never
lain internals. Both fire with `modeline = false`.

                                                            *User-LainAttach*
LainAttach              Fires once per attach, deliberately LAST: by the
                        time your callback runs, every :Lain* runtime
                        command and autocmd exists, so config reacting to
                        LainAttach may call any of them. The payload
                        (`ev.data`):

                          buffers      the full lain:// buffer-name set, in
                                       render order (names, never buffer
                                       numbers -- buffers are created lazily
                                       by their first render)
                          gem_version  the lain gem's version string
                          protocol     the contract the running runtime
                                       actually speaks

                        Trust `data.protocol` as the runtime's version.
                        `g:lain_rpc_version` is only the gem's CLAIM -- the
                        token the gem injected at attach -- and a mismatched
                        runtime has already warned about it; the payload
                        field is what the running Lua really speaks.

                                                            *User-LainRender*
LainRender              Fires after every landed render; `ev.data` carries
                        `name` (the lain:// buffer name) and `buf` (its
                        buffer number).

                        Note: attach PRIMES every view, so expect a burst of
                        LainRender events at attach time -- one per primed
                        view (six today) -- before the agent has done
                        anything. Do not treat that burst as agent activity.

------------------------------------------------------------------------------
6.2 BUFFERS AND b:lain_view                                     *lain-buffers*
                                                                 *b:lain_view*

The runtime owns six buffers: `lain://journal` (append-only tool journal),
`lain://timeline`, `lain://workspace`, `lain://diff`, `lain://inbox` (all
read-only projections), and `lain://request`, the one editable buffer (edit
it, then `:LainResend`). A seventh, `lain://compose`, appears only while you
are composing -- see |lain-compose|.

A `lain://question` buffer appears the same way while you are answering a
question set -- see |lain-question|.

The read-only record views share the single `lain` filetype; `b:lain_view`
names the specific view on EVERY lain:// buffer, and is set before the
FileType autocmd fires. `lain://inbox` also carries
`b:lain_view_generation`, the rendering it is currently showing, which its
gestures send back to lain. Dispatch on it: >lua

    vim.api.nvim_create_autocmd("FileType", {
      pattern = "lain",
      callback = function(ev)
        local view = vim.b[ev.buf].lain_view  -- e.g. "lain://timeline"
      end,
    })
<
`]]` / `[[` jump between records in the journal, timeline, and inbox.

------------------------------------------------------------------------------
6.3 HIGHLIGHT GROUPS                                         *lain-highlights*

The runtime defines one small namespaced syntax for the `lain`-filetype
buffers -- six groups, each `highlight default link`ed, so a colorscheme or
your own `:highlight link` overrides any of them without a fight:

    group           default link  matches ~
    lainToolName    Function      the journal's tool attribution: the id
                                  leading each "[id stream]" prefix
    lainDigest      Identifier    the Store's "blake3:..." digest shape
    lainRole        Keyword       user/assistant opening a timeline turn line
    lainEventKind   Type          event kinds (turn, spawn, message,
                                  snapshot, tool_use, tool_result) plus the
                                  journal's stream words (stdout/stderr)
    lainAge         Comment       the inbox's "12s"/"3m"/"1h" ages
    lainSender      Constant      inbox sender attribution: the text leading
                                  the double-space-padded age

------------------------------------------------------------------------------
6.4 RUNTIME COMMANDS                                   *lain-runtime-commands*

Defined by the runtime at attach (they do not exist before it): `:LainSend`,
`:LainResend`, `:LainContext`, `:LainReply {answer}`, `:LainOpen`, `:LainPin`,
`:LainVersion`, `:LainReviewOpen`, and -- only meaningful inside a review
buffer lain opened (|lain-review|) -- `:LainAnnotate` and `:LainReviewDone`.

In `lain://inbox`, `r` and <CR> both run `:LainOpen`, which opens the question
set your cursor is on in `lain://question` (|lain-question|) for you to tick
and `:w`. Answer one and lain opens the next set you have NOT answered; answer
the last and you are left at the inbox.

A row does not clear when you write it. It clears when the agent that asked has
taken your answer -- a whole model round trip later -- so the set you just
submitted stays listed for a moment. That is the list being honest, not the
write failing. Pressing <CR> on such a row says so and opens nothing: reopening
it would replace what you wrote with a blank document.

`:LainReply {answer}` still answers the OLDEST pending question -- not the one
under your cursor -- as a hand-typed one-liner. A set of several questions has
no single-line answer, so the keys are the way to answer one.

The gesture carries your cursor's line AND the rendering the buffer is holding
(`b:lain_view_generation`, stamped by lain on every inbox render). Both are
needed: the inbox retires rows as questions are answered, so a line number
alone names a position in a listing that may already have moved. A gesture from
a rendering lain no longer holds is refused, and says so, rather than opening
whatever now sits on that line.

In `lain://timeline`, `p` runs `:LainPin`: the turn under the cursor is pinned,
which is a standing instruction that compaction may not elide it. It carries no
rendering stamp and needs none -- a timeline only ever grows, so a line names
one turn forever.

Both are ordinary global commands reading the CURRENT window's cursor, so each
refuses outside the buffer it is about rather than acting on whatever happens
to sit on that line somewhere else.

                                                            *:LainReviewOpen*
                                                              *lain://review*

In `lain://review` -- the changeset review's sidebar, opened in its own tabpage
beside your session -- <CR> runs `:LainReviewOpen`, which opens the file your
cursor is on at its first hunk. It carries your cursor's line AND the rendering
the buffer is holding (`b:lain_view_generation`), for the reason `:LainOpen`
does: sidebar rows move every time the scope toggles or a mark redraws a row,
so a line number alone names a position in a listing that may already have
changed. A gesture from a rendering lain no longer holds is refused, and says
so, rather than opening whatever now sits on that line.

The sidebar has two scopes. Cumulative is one flat file list. The commit walk
shows each commit's own `+added -deleted` and, beneath it, the files whose
hunks are reachable at that commit -- which is NOT the same as what that commit
authored, and the buffer's first line says so. Rows that name no file (the
legend, a commit header) refuse the gesture rather than opening something else.

Two more things the walk cannot tell you, and does not pretend to. A MERGE's
own `+added -deleted` is the whole side branch, so `+9 -9  Merge branch 'side'`
can outrank the commit that actually wrote the code; lain cannot suppress it,
because the changeset carries no parent count and guessing from a subject line
is not a fact. And the `[x]`/`[~]`/`[ ]` marker on a file under a commit is
that file's state across the WHOLE changeset, not its state within that commit.
A commit listing no files at all is normal: attribution is per FILE, last
writer wins, so a merge absorbs everything it re-reports and the commit that
authored it shows `(no hunks reachable here)` with its numstat still beside it.

It is an ordinary global command reading the CURRENT window's cursor, so it
refuses outside `lain://review` rather than acting on whatever happens to sit
on that line somewhere else.

------------------------------------------------------------------------------
6.5 COMPOSING A MESSAGE (PROTOCOL 8)                            *lain-compose*
                                                              *lain://compose*

Press CTRL-G at lain's terminal prompt and whatever you have typed so far
opens here, in a split, focused. Write it back with `:w`; the edited text
becomes the text at the prompt, where YOU press <CR> to send it. lain never
submits it for you.

`lain://compose` is the one lain:// buffer you can `:write`. It is 'acwrite'
and named, so `:w` fires a |BufWriteCmd| that hands the bytes back over RPC
rather than touching any file -- nothing is ever written to disk. It is not
in the |User-LainAttach| buffer set and is not created at attach: it exists
only between CTRL-G and the round trip finishing.

                                                          *lain-compose-abandon*
Close it without writing (`:bd`, `:bw`, or quitting) and NOTHING is sent.
Your draft is kept, not dispatched -- deciding against a draft in the editor
must never put it in front of the model. The same holds if the round trip
times out.

If the write cannot reach lain, `:w` FAILS and the buffer stays 'modified',
so nvim refuses to discard text nobody received: `:bdelete` and `:bwipeout`
answer |E89|, and a last-window quit is refused. A plain `:q` still works --
the buffer is hidden, not abandoned -- so your text is still there under
`:buffer lain://compose`.

Note: `:wall`, and autosave plugins that issue a timed `:w`, DO fire the
write and settle the round trip -- on whatever is in the buffer at that
moment, half-typed or not. `:w` being the gesture is the point, so this is a
known limitation rather than a bug. Switching away from the buffer is safe
even with 'autowriteall': the buffer is hidden, not abandoned, so no write
fires.

------------------------------------------------------------------------------
6.6 ANSWERING A QUESTION SET (PROTOCOL 8)                      *lain-question*
                                                             *lain://question*

The agent asks in SETS: one question or several in a single ask, each with a
markdown body of its own, a closed list of options, and a stated number of them
you may pick. A set arrives as one row in `lain://inbox`, attributed to whoever
asked it -- the session's own agent, or a subagent it spawned -- and is
answered by editing a document: tick a checkbox, write why underneath, `:w`.

Open one with <CR> or `r` on its inbox row (|lain-runtime-commands|). It
renders here folded one fold per question, with the FIRST question open and the
cursor on it: a form is filled from the top.

A question reads like this: >

    ## `rollback` (choose one)
    The migration is half applied. What should I do?

    - [ ] `retry` Run it again from the top
    - [x] `revert` Roll it back and stop
      staging carries the same schema, so a revert costs us nothing

<
The heading names the question and how many options it takes: "choose one",
"choose any", or "write your answer below" for a question offering none.
Everything from the heading down to the options is the agent's own text and is
compared byte for byte when you submit, so it cannot be edited. Two things are
yours: the character inside a checkbox, and prose indented exactly two spaces
beneath an option. The buffer sets 'expandtab', 'shiftwidth' and 'softtabstop'
so that indent is what you type whatever your own config does.

                                                             *lain-question-x*
`x` on an option line ticks it, and un-ticks one already ticked. On a "choose
one" question, ticking also clears the sibling it replaces. Anywhere else in
the buffer -- and this buffer is one you type prose into -- `x` is vim's own
`x`, count and register included, so `"a3x` still deletes three characters into
register a. Both halves repeat with `.`.

Nothing leaves the editor until you write. `:w` submits the document as it
stands; the answer goes to the agent that asked, and lain opens the next set
you have not answered -- or leaves you at the inbox when that was the last one.

A `:w` is REFUSED in two cases, and nothing is submitted in either:

  - nothing in the buffer has been typed. A plain `:w` there would answer
    every question as unanswered, which is a decision rather than a default,
    and a stray `:wall` or an autosave plugin must not make it for you.
    Declining the whole set stays available, deliberately, as `:w!`.
  - a line the grammar has no slot for. The message names the line and what
    was expected there, and the buffer stays 'modified' holding your text
    exactly as you left it. Nothing re-renders over a refused write, because
    the text you have to go fix is the only copy of it -- which is also what
    happens when the write cannot reach lain at all.

                                                       *lain-question-abandon*
Close the buffer without writing (`:bd!`, `:bw!`, `:q!`, or quitting nvim) and
NOTHING is submitted: the set is still pending and still listed in the inbox.
`:close` and `:enew` do not abandon it -- the buffer is hidden, not unloaded --
so `:buffer lain://question` is always the way back to what you were writing.

One set is open at a time. While you hold an unanswered one, opening another
says so and opens nothing rather than replacing what you have typed. The
buffer also carries the set's own content digest, so a write whose set was
answered elsewhere in the meantime -- at the terminal, or by you a moment ago
-- is refused rather than filed against whichever set is open now.

The terminal answers the same sets, and differently: `/inbox` prints this same
document and reads a typed reply, which answers the WHOLE set in prose rather
than by selection. Ticking is the editor's gesture, and the only one.

------------------------------------------------------------------------------
6.7 REVIEWING A DOCUMENT (PROTOCOL 8)                            *lain-review*
                                                              *:LainAnnotate*
                                                             *:LainReviewDone*

lain hands a document back to you by opening the REAL FILE -- not a `lain://`
buffer -- in a split, focused, with the review it belongs to stamped on the
buffer (`b:lain_review_generation`, `b:lain_review_epic_slug`). While you hold
it, lain does not write it.

    :LainAnnotate           Prompt for a note and attach it to the line the
                            cursor is on, shown as virtual text. The note
                            travels with the line as you keep editing.

    :LainReviewDone         Hand the document back. Refuses while the buffer
                            is 'modified': lain settles the review from what
                            is ON DISK, so save first. Your annotations ride
                            along with it.

Both commands refuse outside a review buffer. lain DOES ship an asker -- an
epic hands the agent a request_review tool -- but the editor it would open a
review in is deliberately left unwired, so the request is announced and never
rendered here. The editor half described above is complete and is what that
asker will drive once the two are connected. So treat this section as the
contract your config can already hook (the buffer variables above are set, and
the commands exist at attach), not as a workflow you can start today.

6.8 READING A CHANGESET                                     *lain-review-diff*

A changeset review opens each changed file as a PAIR. On the right is the real
file: 'buftype' is empty, so your language server and treesitter attach to it
exactly as they would to a file you opened yourself, and you can edit and `:w`
it. On the left is a read-only `nofile` buffer named `lain://review/OLD/{path}`
holding that file as of the merge base.

Both windows are in nvim's native diff mode, so 'foldmethod' is "diff" --
unchanged regions fold away and `zo`/`zr` expand them -- `]c`/`[c` walk the
changes, and `do`/`dp` work as they always do. Opening a file focuses the new
side on the line the review sent you to, opening just enough fold to show it.

Each side carries which side it is, which commit it came from, and which file:

    b:lain_review_side          "old" or "new"
    b:lain_review_revision      the commit that side was read at
    b:lain_review_path          the file's path, as the review names it

Those variables are true of the file you are looking at and of nothing else:
they are withdrawn from a file as soon as you move on from it.

Paths are resolved against the project directory as it was when lain attached,
so `:cd`, `:lcd` and directory-changing plugins cannot send a review to the
wrong file. Set `g:lain_review_root` if you started nvim outside the repository
you are reviewing.

The old side cannot be written -- `:w` fails with E382 -- because those bytes
are history, and lain settles the review from the revision rather than from a
file. The pair is reused as you move between files, and the old side's buffer
is wiped as it is replaced, so a long review leaves no buffer per file behind.

------------------------------------------------------------------------------
6.9 FOLDS                                                         *lain-folds*

The record-shaped views -- `lain://timeline` (one fold per turn),
`lain://journal` (one fold per `[id stream]` output run), `lain://inbox` (one
fold per pending question set), `lain://question` (one fold per question in the
set) -- set window-local expr folds when first shown: every record starts
closed but one, and which one differs by view. A LOG's live record is its last,
so the timeline, the journal and the inbox open the newest; a FORM's is its
first, so a question document opens the question at the top (|lain-question|).

That default applies once, at display; renders never re-fold, so turns you open
(|za|/|zo|) and |zR| stick while the session streams -- at most lain re-opens
the record it left open after a render. Because a turn or a question set's
inbox row is often a single line, lain sets 'foldminlines' to 0, so single-line
records render |hl-Folded| at rest -- the fold summary line (the record's own
first line, plus a hidden-line count when there is one) is what you see, not
blank collapse markers. Fold boundaries are exactly the |]]|/|[[| record
boundaries. When the window moves on to another buffer, your previous fold
options are restored. `lain://request`, `lain://diff`, and `lain://workspace`
are left to your own fold config.

Set `vim.g.lain_fold = false` to opt out (it also un-installs live,
mid-session); set `vim.g.lain_foldlevel` >= 1 to keep every record open at
rest; and for per-render control define an autocmd on `User LainRender` -- it
fires after lain's fold upkeep, so whatever it opens or closes wins.

==============================================================================
7. WITHOUT THE PLUGIN                                      *lain-zero-install*

The plugin is optional sugar. A bare editor started as >

    nvim --listen /tmp/some.sock
<
and a `lain chat --nvim` pointed at that socket attach exactly the same:
runtime injected, buffers, commands, events, highlights -- everything in
|lain-contract|. The plugin adds only the socket convention, the two
functions, and |:LainStart|.
